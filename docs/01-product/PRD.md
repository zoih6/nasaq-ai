## 1. غرض هذه الوثيقة

تحوّل هذه الوثيقة رؤية نَسَق إلى متطلبات منتج قابلة للتصميم والتنفيذ والاختبار. وهي تجيب عن:

- ما المشكلة التي نحلها، ولمن؟
- ما الذي يدخل في المنتج وما الذي يُؤجل؟
- ما السلوك المتوقع من كل وحدة؟
- ما الفرق بين النموذج التفاعلي والمنتج المتصل فعليًا؟
- كيف نعرف أن التجربة أو الإصدار جاهز؟
- ما القياسات والضوابط المطلوبة للثقة والأمان والتكلفة؟

### 1.1 ما لا تفعله هذه الوثيقة

لا تحدد هذه الوثيقة التفاصيل النهائية للألوان والمكونات، ولا مخططات قاعدة البيانات التفصيلية، ولا عقود API النهائية. توضع هذه في:

- `docs/02-design/DESIGN.md`
- `docs/03-architecture/FRONTEND-ARCHITECTURE.md`
- `docs/03-architecture/CONTRACTS.md`
- `docs/03-architecture/PERMISSIONS.md`
- `docs/03-architecture/SECURITY.md`

### 1.2 دلالات الأولوية

| المصطلح | المعنى |
|---|---|
| **MUST / P0** | شرط إطلاق للإصدار المحدد؛ لا يُعد الإصدار مكتملًا بدونه |
| **SHOULD / P1** | مهم جدًا ويأتي مباشرة بعد P0؛ يمكن تأجيله بقرار موثق |
| **COULD / P2** | تحسين لاحق لا يمنع الإطلاق |
| **لن يُنفذ الآن** | خارج النطاق الحالي عمدًا |

### 1.3 مبدأ التتبّع

لكل متطلب معرف ثابت مثل `CHAT-004`. يجب استخدام هذه المعرفات في التصميم، عقود البيانات، قصص التطوير، الاختبارات، وتقارير التسليم.

## 2. الملخص التنفيذي

نَسَق AI مساحة عمل عربية للمحترفين والفرق الصغيرة تجمع:

1. **محادثة متعددة النماذج** مع اختيار ومقارنة وتوجيه شفاف.
2. **مشاريع ذات سياق موحد** تضم المحادثات والملفات والمعرفة والوكلاء والتدفقات.
3. **وكلاء ينفذون مهامًا** عبر خطة وأدوات وموافقات ومخرجات قابلة للتسليم.
4. **تدفقات مرئية** تحول العمل المتكرر إلى عملية قابلة لإعادة التشغيل والمراقبة.
5. **معرفة ومصادر** مرتبطة بالمشروع مع إسناد واضح.
6. **إدارة نماذج وتكلفة** عبر BYOK أو رصيد المنصة مع سجل استهلاك قابل للمراجعة.

المنتج ليس واجهة تغليف بسيطة لعدة APIs. القيمة الجوهرية هي استمرار السياق والانتقال الطبيعي:

> **Chat → Agent → Flow**

يستطيع المستخدم أن يبدأ بسؤال، ثم يفوض مهمة مركبة لوكيل، ثم يحول الطريقة الناجحة إلى تدفق متكرر للفريق.

## 3. المشكلة والسياق

### 3.1 مشكلات المستخدم الحالية

المحترف أو الفريق الصغير الذي يستخدم أدوات AI متعددة يواجه عادةً:

- حسابات وواجهات وسجلات منفصلة لكل مزود.
- تكرار رفع الملفات وشرح السياق من جديد.
- صعوبة معرفة النموذج الأنسب لمهمة معينة.
- عدم وضوح التكلفة قبل التنفيذ وبعده.
- عدم وجود انتقال من «إجابة» إلى «مهمة منفذة» ثم إلى «عملية متكررة».
- وكلاء يعملون كصندوق أسود دون خطة واضحة أو حدود أو إيصالات تنفيذ.
- أتمتة مرئية منفصلة عن المحادثة والمعرفة والنماذج.
- دعم عربي وRTL سطحي أو ملحق متأخرًا.
- صعوبة مشاركة العمل والحوكمة داخل فريق صغير دون أدوات enterprise ثقيلة.

### 3.2 الفرصة

يمكن لنَسَق أن يصبح طبقة العمل اليومية التي توحد النموذج والسياق والتنفيذ والتكلفة، مع تجربة عربية أصلية وضوابط ثقة ظاهرة للمستخدم بدل إخفائها في الإعدادات أو الوثائق القانونية.

### 3.3 فرضية المنتج

إذا وفّرنا للمحترفين والفرق الصغيرة مساحة واحدة تسمح لهم باختيار أو مقارنة النماذج، حفظ سياق المشروع، تفويض المهام لوكلاء مضبوطين، وتحويل النتائج الناجحة إلى تدفقات قابلة للتكرار، فسوف يقل تشتت الأدوات ووقت إعادة الشرح، ويزداد عدد النتائج القابلة للتسليم والعمليات المتكررة بثقة وتكلفة أوضح.

## 4. الرؤية والوعد والتموضع

### 4.1 الرؤية

أن تصبح نَسَق مساحة العمل العربية الموثوقة التي تنظم العلاقة بين الإنسان والنماذج والوكلاء والأتمتة.

### 4.2 الوعد

> **كل نماذجك ووكلائك وتدفقاتك، في مساحة عمل واحدة.**

### 4.3 التموضع

نَسَق هو **AI Work Operating Layer** للمحترفين والفرق الصغيرة، وليس:

- مجرد دردشة متعددة النماذج.
- مجرد منشئ وكلاء.
- مجرد لوحة أتمتة.
- مجرد سوق prompts أو skills.

### 4.4 عوامل التميز المطلوبة

1. سياق مشروع مشترك بين Chat وAgents وFlow وKnowledge.
2. انتقال مباشر من المحادثة إلى الوكيل، ومن التشغيل الناجح إلى التدفق.
3. مقارنة نماذج قابلة للفعل، لا عرض إجابات جنبًا إلى جنب فقط.
4. توجيه شفاف يوضح النموذج والمزود ومصدر الدفع والسبب والتكلفة.
5. موافقات وصلاحيات وحدود وإيصالات تنفيذ للوكلاء.
6. تجربة عربية أصلية مع إنجليزية مكافئة.
7. تكلفة مفهومة على مستوى الرسالة والتشغيل والمشروع والفريق.

## 6. ما ليس هدفًا في المرحلة الحالية

العناصر التالية خارج نطاق الـPrototype والـBackend MVP، ولا تُضاف دون قرار تغيير نطاق:

1. وكيل استخدام حاسوب عام وغير محدود.
2. تشغيل أوامر shell أو كود غير موثوق خارج sandbox مضبوط.
3. multi-agent swarms مستقلة طويلة العمر.
4. سوق عام للوكلاء والمهارات والتدفقات.
5. دعم عشرات المزودين عند الإطلاق الأول.
6. استضافة داخلية `on-premise` أو بنية enterprise كاملة.
7. SSO/SAML وSCIM وسياسات مؤسسات متقدمة.
8. تطبيقات هاتف أصلية؛ الويب المتجاوب أولًا.
9. منافسة أدوات IDE والوكلاء البرمجية الكاملة في الإصدار الأول.
10. إنشاء أو تحرير فيديو وموسيقى كمسار منتج أساسي.
11. منح Flow قدرة كتابة خارجية خطرة دون موافقة وسياسة واضحة.
12. وعود قانونية أو تنظيمية غير مثبتة مثل «امتثال كامل» قبل التدقيق الرسمي.

## 7. المستخدمون المستهدفون

### 7.1 الشخصية الأساسية A — المحترف المعرفي المستقل

**أمثلة:** باحث، مستشار، محلل، مسوّق، كاتب، مدير منتج، مصمم، رائد أعمال.

**احتياجاته:**

- الحصول على إجابة أو مسودة أو تحليل بسرعة.
- مقارنة النتائج عندما تكون الجودة أو الدقة مهمة.
- حفظ الملفات والسياق حسب العميل أو المشروع.
- تفويض بحث أو تحليل طويل دون متابعة كل خطوة.
- معرفة التكلفة وعدم الاشتراك في عدة خدمات منفصلة.

**أسباب الفشل المحتملة:** واجهة معقدة، مصطلحات تقنية مفرطة، نتائج بلا مصادر، تكلفة غامضة، أو وكيل يحتاج مراقبة مستمرة.

### 7.2 الشخصية الأساسية B — قائد فريق عربي صغير

**أمثلة:** قائد فريق محتوى، وكالة، استوديو تصميم، فريق عمليات، شركة ناشئة من 3–20 عضوًا.

**احتياجاته:**

- مشاركة سياق وملفات وأدوات دون مشاركة مفاتيح سرية.
- توحيد طريقة تنفيذ المهام المتكررة.
- معرفة من شغّل ماذا وكم كلف.
- وضع ميزانيات وموافقات وصلاحيات بسيطة.
- تحويل أفضل طريقة عمل إلى قالب وكيل أو Flow للفريق.

**أسباب الفشل المحتملة:** صلاحيات ضعيفة، خلط مساحات العملاء، عدم وجود سجل تدقيق، أو صعوبة إدارة التكلفة.

### 7.3 الشخصية الثانوية C — المنشئ التقني

**أمثلة:** مطور full-stack، مهندس أتمتة، مشغل تقني داخل فريق صغير.

**احتياجاته:**

- BYOK، اختيار المزود، routing واضح، webhooks وAPIs.
- بناء وكلاء وتدفقات قابلة للنسخ والإصدار والاختبار.
- رؤية logs وpayloads المنقحة ونتائج كل خطوة.
- عقود واضحة وقابلية تصدير لاحقة.

### 7.4 غير المستهدف أولًا

- المؤسسات التي تشترط on-premise أو سيادة بيانات خاصة قبل التجربة.
- المستخدم الذي يريد chatbot مجانيًا بسيطًا فقط.
- المستخدم الذي يريد وكيلاً مستقلاً بصلاحيات حاسوب كاملة دون إشراف.

## 9. مبادئ المنتج الحاكمة

1. **المهمة قبل النموذج:** يبدأ المنتج مما يريد المستخدم إنجازه، لا من قائمة مزودين.
2. **الشفافية قبل الذكاء الخفي:** نعرض النموذج والمزود ومصدر الدفع والتكلفة وسبب التوجيه.
3. **الخطة ليست Chain of Thought:** نعرض خطوات عملية وقرارات وأدلة، لا سردًا داخليًا مزعومًا.
4. **لا أثر خارجي بلا سياسة:** القراءة والكتابة والحذف والشراء والنشر مستويات مختلفة.
5. **الموافقة في اللحظة المناسبة:** لا نغرق المستخدم بتأكيدات منخفضة المخاطر، ولا نخفي التأثيرات العالية.
6. **السياق أصل مشترك:** الملفات والمعرفة والقرارات تتبع المشروع، لا نافذة المحادثة فقط.
7. **التكلفة جزء من UX:** تقدير قبل التشغيل، تحديث أثناءه، وتسوية فعلية بعده.
8. **العربية ليست ترجمة:** IA والمصطلحات والتخطيط والاختبار تبدأ بالعربية.
9. **النتائج قابلة للتسليم:** كل تشغيل مهم يجب أن ينتج artifact أو receipt أو قرارًا محفوظًا.
10. **تدرج التعقيد:** يبدأ المستخدم بمحادثة بسيطة ويكشف النظام القدرات الأعمق عند الحاجة.

| تشغيل التدفق `Flow Run` | تنفيذ نسخة منشورة أو مسودة من Flow على مدخلات معينة |
| مصدر المعرفة `Knowledge Source` | ملف أو URL أو نص مفهرس يمكن استرجاعه مع إسناد |
| رصيد المنصة `Managed Credits` | رصيد يدفع استدعاءات مزودين تديرهم المنصة |
| BYOK | مفتاح API يضيفه المستخدم ويُستخدم وفق نطاق وسياسة واضحة |

## 11. مراحل المنتج ونطاق الإصدارات

### 11.1 الإصدار A — Frontend Interactive Prototype

**الغرض:** اعتماد IA والتجربة والعقود المرئية قبل الاستثمار في الخدمات الخلفية.

**يشمل:**

- كل الوحدات الرئيسية قابلة للتنقل والتفاعل.
- بيانات واقعية وهمية وMock API موحد.
- العربية والإنجليزية وRTL/LTR.
- سيناريوهات Chat وCompare وAgent Run وFlow Run كاملة بصريًا.
- حالات loading وempty وerror وsuccess وpermission وquota.
- تصميم متجاوب ووصولية أساسية واختبارات متصفح.
- نماذج شاشات BYOK والفوترة دون قبول أسرار أو مدفوعات حقيقية.

**لا يشمل:**

- استدعاء مزود AI حقيقي.
- تخزين مفتاح حقيقي.
- دفع أو تعبئة رصيد حقيقية.
- تنفيذ أداة أو webhook أو بريد أو كتابة خارجية.
- مصادقة production أو فصل مستأجرين فعلي.

### 11.2 الإصدار B — Backend MVP / Private Alpha

**الغرض:** تمكين مجموعة صغيرة مدعوة من إنجاز مهام حقيقية بأقل سطح آمن مفيد.

**يشمل P0:**

- Auth ومساحات عمل ومشاريع.
- Chat streaming مع ثلاثة مزودين/عائلات نماذج على الأقل، حسب العقود والتوفر.
- اختيار يدوي ومقارنة نموذجين أو ثلاثة.
- رفع ملفات محدود ومعالجة آمنة.
- BYOK + Managed Credits.
- Model registry وusage ledger وbudgets أساسية.
- وكيل بحث واحد مع مصادر وخطة وموافقات ومخرجات.
- سجل تشغيل وإيصالات تنفيذ وإيقاف/إلغاء.
- Flow محدود: تشغيل يدوي، عقد خطية/شرط بسيط، دون كود حر أو دورات.
- Audit log للأحداث الحساسة.

### 11.3 الإصدار C — Private Beta

**يشمل P1:**

- Knowledge collections وRAG أوسع.
- وكلاء إضافيون للملفات والتحليل والمحتوى.
- أدوات واتصالات منتقاة.
- Flow versions وwebhooks وschedule وضوابط retry.
- أدوار فريق أدق ومشاركة artifacts.
- تقارير استخدام وفواتير وتنبيهات أكثر نضجًا.
- Smart routing بعد توفر بيانات تقييم وتكلفة كافية.

### 11.4 ما بعد Beta

- Marketplace منسق بعد بناء provenance وتوقيع ومراجعة أمان.
- code agent داخل sandbox قوي.
- enterprise controls وSSO وdata residency إضافية.
- API عامة وSDK.
- تطبيق هاتف أصلي إذا أثبت الويب حاجة واضحة.

## 28. الرحلات الحرجة

### 28.1 من التسجيل إلى أول نتيجة

1. يختار المستخدم العربية/الإنجليزية ونوع استخدامه.
2. ينشئ مساحة أو يستخدم الشخصية.
3. يختار البدء برصيد/عرض تجريبي أو تأجيل BYOK.
4. يرى prompt starters مرتبطة بدوره، لا gallery عامة فقط.
5. يرسل رسالة ويشاهد النموذج ومصدر الدفع.
6. يحصل على إجابة ويمكنه حفظها في مشروع أو مقارنتها.

**معيار النجاح:** ينجز مستخدم جديد المسار دون شرح خارجي، ويفهم أين يرى النموذج والتكلفة.

### 28.2 مقارنة نموذجين

1. يفتح Compare من composer أو response.
2. يختار نموذجين/ثلاثة ويرى توافق الملفات والتكلفة التقديرية.
3. يرسل المدخل مرة واحدة.
4. يشاهد outputs مستقلة مع progress/cost/source.
5. يختار واحدة للمتابعة أو يطلب synthesis جديدًا.

**معيار النجاح:** لا يظن المستخدم أن synthesis مجاني أو أن أحد النموذجين فائز موضوعيًا.

### 28.3 Chat إلى Agent

1. يختار جزءًا من المحادثة أو المحادثة كلها.
2. يضغط «حوّل إلى مهمة».
3. تعرض صفحة مراجعة الهدف والمدخلات والسياق والأداة والميزانية.
4. يبدأ التشغيل وتظهر الخطة.
5. يتوقف عند موافقة إن لزم.
6. يكتمل بمخرج وإيصال تنفيذ.

**معيار النجاح:** يعرف المستخدم ما نُقل وما لم يُنقل، ويستطيع العودة إلى أصل المحادثة.

### 28.4 إنشاء وكيل بحث وتشغيله

1. يختار Research Agent.
2. يحدد السؤال والنطاق والمصادر المقبولة وشكل التقرير.
3. يراجع خطة وميزانية أولية.
4. يبدأ التشغيل، يتابع المصادر والخطوات العملية.
5. يجيب عن سؤال توضيحي أو موافقة إن ظهرت.
6. يستلم تقريرًا ومصادر وحدود ثقة وتكلفة.

**معيار النجاح:** لا توجد اقتباسات بلا مصدر أو ادعاء اكتمال عندما فشل جزء من البحث.

### 28.5 تشغيل ناجح إلى Flow

1. يفتح run مكتملًا.
2. يختار «حوّل إلى تدفق».
3. يستخرج النظام المدخلات والخطوات والمخرجات المقترحة.
4. يراجع المستخدم العقد والبيانات الحساسة والحدود.
5. يحفظ كمسودة ويختبر بfixture.
6. ينشر النسخة عندما تكون صالحة.

**معيار النجاح:** لا تُنقل أسرار أو نتائج خاصة كقيم ثابتة دون تحذير.

### 28.6 إضافة BYOK

1. يختار المزود ويقرأ شرح التخزين والنطاق.
2. يدخل المفتاح في واجهة آمنة.
3. يختبر الاتصال.
4. يحدد النطاق وfallback.
5. يحفظ ويرى آخر استخدام والحالة دون رؤية المفتاح.
6. يستخدمه في Chat مع badge واضح.

**معيار النجاح:** يفهم المستخدم أن تكلفة المزود قد تكون خارج رصيد نَسَق وأن fallback قد يغيّر مصدر الدفع.

### 28.7 موافقة عالية الأثر

1. يصل run إلى خطوة كتابة/نشر/إرسال.
2. يرى الموافق action preview والهدف والبيانات والتكلفة والمخاطر.
3. يوافق أو يعدل أو يرفض.
4. يسجل القرار ويستأنف أو ينهي run.

**معيار النجاح:** لا يستطيع المستخدم الموافقة دون فهم الإجراء، ولا ينفذ الإجراء مرتين عند إعادة التحميل.

## 29. حالات النظام القياسية

### 29.1 حالة Run موحدة

```text
draft
  → queued
  → planning
  → running
  → waiting_for_input
  → waiting_for_approval
  → running
  → completed | completed_with_warnings | failed | cancelled | expired
```

### 29.2 حالة Approval

```text
pending → approved | denied | edited | expired | revoked
```

### 29.3 حالة Knowledge Source

```text
uploaded → scanning → processing → ready
                         ↘ failed
ready → stale → reprocessing → ready
ready | failed | stale → deleting → deleted
```

### 29.4 حالة Flow

```text
draft → validated → published → deprecated → archived
```

### 29.5 قواعد الحالة

- لا تستخدم الواجهة كلمة «فشل» فقط؛ تعرض المرحلة والسبب وما يمكن استعادته.
- `completed_with_warnings` لا يظهر كنجاح كامل.
- cancel request وcancelled حالتان مختلفتان عند وجود عملية upstream.
- تحديث الصفحة لا يفقد run state أو يكرر الإجراء.
- الحالات النصية لا تعتمد على اللون وحده.

## 35. التحليلات ومؤشرات النجاح

### 35.1 North Star Metric

**Weekly Successful Outcomes — النتائج الناجحة الأسبوعية**

تُحسب النتيجة عندما يكتمل Chat/Agent/Flow ويقوم المستخدم بواحد أو أكثر من:

- حفظ أو تصدير artifact.
- متابعة النتيجة في رسالة لاحقة ذات معنى.
- مشاركتها أو إضافتها إلى مشروع.
- تعليمها كمفيدة.
- تحويلها إلى Agent أو Flow.

لا تُحسب retries الآلية أو الرسائل الفارغة أو تشغيلات العرض.

### 35.2 مؤشرات المنتج

| الفئة | المؤشر |
|---|---|
| Activation | إكمال أول Chat ناجح، ثم حفظ/مقارنة/إنشاء مشروع خلال 24 ساعة |
| Time to Value | الزمن من اكتمال التسجيل إلى أول successful outcome |
| Adoption | مستخدمون يستعملون وحدتين أو أكثر خلال أسبوع |
| Compare Value | نسبة المقارنات التي تنتهي باختيار/متابعة أو synthesis |
| Agent Success | تشغيلات مكتملة أو مكتملة بتحذير ضمن budget مقابل الفشل/الإلغاء |
| Reuse | تحويل Chat إلى Agent، وتحويل Run إلى Flow، وإعادة تشغيل قالب |
| Trust | نسبة موافقات مفهومة، نزاعات التكلفة، fallback surprises، وشكاوى المصدر |
| Retention | WAU/MAU واحتفاظ الأسبوع الرابع حسب persona |
| Business | استهلاك credits، نسبة BYOK، gross margin لكل فئة، وتحويل الخطة |
| Reliability | provider errors، timeout، duplicate ledger، stuck runs |

### 35.3 أهداف usability للـPrototype

- ينجز غالبية المشاركين المسارات الخمسة الحرجة دون مساعدة مباشرة.
- يميز المشاركون بين Chat وAgent وFlow بلغتهم.
- يستطيع المستخدم تحديد النموذج ومصدر الدفع والتكلفة من الواجهة.
- يفهم الموافق ما سيحدث قبل اعتماد فعل عالي الأثر.
- لا توجد مشكلة RTL أو وصولية تمنع إكمال مسار حرج.

الأرقام النهائية للنجاح تعتمد بعد أول جولة baseline؛ لا نختلق نسبة قبل الاختبار.

## 36. متطلبات الـFrontend Prototype

### 36.1 بنية البيانات الوهمية

يجب أن تأتي الشاشات من contracts وfixtures وMock Service Worker أو طبقة مماثلة، لا من كائنات مختلفة داخل كل صفحة.

كل سيناريو مهم يجب أن يملك fixture محددًا وقابلًا لإعادة التشغيل:

1. مستخدم جديد بلا مشاريع.
2. محترف لديه مشروع ومحادثات وملفات.
3. فريق صغير متعدد الأدوار.
4. مقارنة نموذجين ناجحة.
5. نموذج غير متاح وfallback غير مفعّل.
6. رصيد منخفض وحد ميزانية متجاوز.
7. Agent run ينتظر سؤالًا.
8. Agent run ينتظر موافقة عالية الأثر.
9. Agent run مكتمل بمصادر وartifact.
10. Agent run فاشل جزئيًا مع recovery.
11. Flow صالح وتشغيل ناجح.
12. Flow بعقدة ناقصة تمنع النشر.
13. Knowledge source processing/failed/stale.
14. مفتاح BYOK صالح/فاشل/ملغى — كلها بيانات وهمية.
15. مستخدم viewer يحاول فعلًا غير مسموح.

### 36.2 بيانات العرض الموحدة

لمنع lorem ipsum والواجهات المختلقة، يستخدم الـprototype قصة عرض متماسكة، مثل:

- مساحة العمل: **فريق أفق**.
- المشروع: **دراسة إطلاق خدمة في السوق السعودي**.
- المحادثة: مقارنة نماذج لتحليل السوق.
- الوكيل: **باحث السوق**.
- المخرج: تقرير فرص ومخاطر مع مصادر.
- التدفق: **رصد المنافسين الأسبوعي**.

تُراجع هذه الأسماء والمحتويات في `CONTENT.md` قبل اعتمادها النهائي.

### 36.3 متطلبات العقود

- TypeScript strict.
- مخططات runtime validation للحدود المهمة.
- IDs وتواريخ وحالات ثابتة بين الوحدات.
- money/usage كأنواع لا أرقام عائمة عشوائية.

| مراجعة قانونية/خصوصية | شرط الأسواق وسياسات البيانات والفوترة |

## 41. المخاطر وخطط التقليل

| الخطر | الاحتمال/الأثر | خطة التقليل |
|---|---|---|
| المنتج يبدو كمجموعة أدوات معقدة | مرتفع/مرتفع | progressive disclosure، Chat نقطة بداية، اختبارات IA ومهام لا demo تقني |
| واجهة جميلة بلا قيمة متصلة | متوسط/مرتفع | prototype بعقود وسيناريوهات end-to-end ومعايير نجاح مهمة |
| تفاوت جودة المزودين | مرتفع/مرتفع | model registry، evals، manual override، receipts، وعدم ادعاء نموذج أفضل مطلقًا |
| تكلفة غير متوقعة | مرتفع/مرتفع | estimate/reservation/actual، budgets، hard limits، مصدر دفع ظاهر |
| فشل agent أو توقفه | مرتفع/متوسط | durable events، حدود، pause/retry، partial artifacts وrecovery |
| prompt injection عبر ويب/ملف | مرتفع/مرتفع | فصل التعليمات عن البيانات، tool policies، egress، approvals وred-team |
| تسرب مفاتيح BYOK | منخفض/كارثي | vault/KMS، عدم الإرجاع أو logging، least privilege، rotation وsecurity review |
| side effect مكرر | متوسط/مرتفع | idempotency، approval tokens، ledger/run receipts واختبارات replay |
| RTL يعمل شكليًا فقط | متوسط/مرتفع | Arabic-first content، logical CSS، screenshots واختبارات قارئ شاشة |
| scope creep قبل إثبات الأساس | مرتفع/مرتفع | P0/P1 واضح، launch gates، لا marketplace/swarms/computer use مبكرًا |
| الاعتماد على مزود واحد | متوسط/مرتفع | adapters وعقود داخلية، لكن دون fallback صامت |
| هامش ربح سلبي مع credits | متوسط/مرتفع | قياس تكلفة فعلية لكل حدث، limits وتسعير قبل التوسع |
| ادعاءات أمان أو امتثال مبكرة | متوسط/مرتفع | صفحة ضوابط فعلية ومخططة، مراجعة قانونية وأمنية قبل الشارات |

## 43. خطة التحقق البحثي

### 43.1 أسئلة يجب اختبارها في الـPrototype

1. هل يفهم المستخدم الفرق بين Chat وAgent وFlow دون شرح طويل؟
2. هل يبدأ من المهمة أم يضيع في model picker؟
3. هل مقارنة النماذج تساعد القرار أم تزيد العبء؟
4. هل يفهم مصدر الدفع وBYOK/fallback؟
5. هل timeline الوكيل يحقق الثقة أم يصبح ضوضاء تقنية؟
6. ما المعلومات اللازمة للموافقة على فعل خارجي؟
7. هل يمكن تحويل run إلى Flow دون معرفة automation مسبقة؟
8. هل يجد الفريق الصغير المشاريع والميزانية والصلاحيات كافية؟
9. هل المصطلحات العربية طبيعية للمحترف وغير مربكة؟
10. ما الذي يجب أن يبقى متاحًا على الهاتف؟

### 43.2 المشاركون

جولة أولى صغيرة لكن متنوعة تشمل:

- محترفين مستقلين يستخدمون أكثر من نموذج.
- قادة فرق صغيرة يديرون ملفات وتكلفة.
- مستخدمين تقنيين جربوا agents أو automation.
- مستخدمًا واحدًا على الأقل يعتمد لوحة المفاتيح أو تقنية مساعدة إن أمكن.

لا تُختلق personas أو اقتباسات أو نسب؛ تحفظ الملاحظات والأدلة مع consent وخصوصية مناسبة.

## 44. Definition of Ready للتطوير

لا تبدأ أي epic كبيرة قبل توفر:

- المتطلبات المرتبطة ومعرفاتها.
- flow أو wireframe مع الحالات الأساسية.
- copy عربي وإنجليزي مبدئي.
- contracts وfixture واضحان.
- permission assumptions.
- analytics events المطلوبة.
- متطلبات a11y وresponsive.
- acceptance tests وحدود out-of-scope.
- قرار حول البيانات الحساسة والأثر الخارجي إن وجدا.

## 45. Definition of Done لكل ميزة

- [ ] تحقق معيار القبول المرتبط بالـPRD.
- [ ] تستخدم contract مشتركًا ولا تنشئ shape محليًا بلا سبب.
- [ ] loading/empty/error/success والقيود اللازمة منفذة.
- [ ] العربية والإنجليزية وRTL/LTR مختبرة.
- [ ] keyboard وfocus وscreen reader semantics مناسبة.
- [ ] responsive على النطاق المستهدف.
- [ ] analytics بلا محتوى حساس.
- [ ] unit/component/integration/e2e بحسب الخطر.
- [ ] لا console errors أو network failures غير المعالجة.
- [ ] security/privacy review عند أسرار أو ملفات أو network أو side effects.
- [ ] receipt يتضمن الأوامر والاختبارات والنتائج والمخاطر المفتوحة.

## 49. الخلاصة التنفيذية

الإصدار الأول من نَسَق يجب أن يثبت ثلاث حقائق فقط قبل توسيع النطاق:

1. يستطيع المستخدم العربي إنجاز عمل مفيد عبر نماذج متعددة دون تعقيد أو غموض تكلفة.
2. يستطيع تحويل محادثة إلى وكيل مضبوط ينتج نتيجة موثقة مع بقاء السيطرة البشرية.
3. يستطيع تحويل العمل الناجح إلى تدفق قابل للتكرار دون أن يصبح خبير أتمتة.

كل ميزة لا تدعم واحدة من هذه الحقائق، أو الأمان والثقة اللازمين لها، تُؤجل حتى يثبت الأساس.
